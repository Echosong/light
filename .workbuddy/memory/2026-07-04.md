## light-codegen Skill vs Light.Generator 对比分析

### 背景
用户要求检测 `light-codegen` skill 能否完全替代 `Light.Generator` 模块，以及该 skill 能否应用到其他大模型。

### 对比结论

**原 Light.Generator 模块（7个服务）:**
1. DtoService → DTO/QueryDTO/ListDTO
2. MapperService → Mapper.java + Mapper.xml
3. ControllerService → Controller
4. ImplService → Service 接口 + 实现
5. ViewService → list.vue / add.vue / info.vue
6. DictionaryService → data.html 数据字典
7. JpaCommentService → 同步数据库表/字段备注（ALTER TABLE）

**light-codegen Skill 覆盖情况:**
- 完全覆盖：DTO(3个)、Mapper(2个)、Controller、Service(2个) — 后端 CRUD 全套
- 部分覆盖：数据字典 data.html（有模板但无全量合并逻辑）
- 未覆盖：
  1. **Vue 视图生成**（list.vue/add.vue/info.vue）— SKILL.md 中标注为"预留"
  2. **数据库备注同步**（JpaCommentService）— 需要 JDBC 连接执行 ALTER TABLE 语句

**结论：不能完全替代。** 后端代码生成可完全替代，但 Vue 前端视图和数据库备注同步缺失。

### 跨大模型兼容性

Skill 内容（SKILL.md 指令 + references 规则 + templates 模板）是 LLM 无关的纯文本：
- **WorkBuddy**：原生支持，自动加载 + 文件读写
- **Cursor/Windsurf/Cline**：SKILL.md 可作为 .cursorrules，有文件读写能力
- **GitHub Copilot**：内容可放入 .github/copilot-instructions.md，IDE 内有文件能力
- **ChatGPT/Claude/Gemini（网页版）**：作为 system prompt 使用，无文件读写需手动保存生成代码

关键差异在"文件读写能力"而非"理解能力"。

## light-codegen Skill 实战测试：SysOrder 代码生成

### 背景
用户要求根据 `SysOrder` Entity 实际运行 skill 生成全套代码，验证 skill 可用性。

### Entity 分析
- `SysOrder.java` — `@MappedSuperclass` 基类，继承 `SysBase`，无 `@AutoEntity` 注解
- tableName = `SysOrder`，className = `Order`（Sys 前缀去除）
- 22 个 `@AutoEntityField` 字段（SysBase 6 + SysOrder 16，排除无 @AutoEntityField 的 orderPrice）
- 4 个 `@InQueryDTO` 字段：memberName/orderNo/outOrderNo(String) + payAmount(BigDecimal)
- 无 `isKeyName=true` → isKey=false，无 getMap 方法
- 无 `@AutoCover` → 不覆盖已有文件
- isBigDecimal=true

### 生成结果（11 个文件）
**后端（8个）:**
1. `Light.Packet/.../dto/order/OrderDTO.java` — 全字段 DTO
2. `Light.Packet/.../dto/order/OrderQueryDTO.java` — 4个查询字段
3. `Light.Packet/.../dto/order/OrderListDTO.java` — 列表 DTO
4. `Light.Entity/.../mapper/OrderMapper.java` — Mapper 接口
5. `Light.Entity/.../resources/mapper/OrderMapper.xml` — 含 4 个 sql_where 条件
6. `Light.Admin/.../controller/OrderController.java` — 5 个方法（无 getMap）
7. `Light.Server/.../service/OrderService.java` — Service 接口
8. `Light.Server/.../service/impl/OrderServiceImpl.java` — Service 实现

**前端（3个）:**
9. `light-view/src/views/system/order/list.vue` — 22列+操作列(fixed:right)，4个查询表单项
10. `light-view/src/views/system/order/add.vue` — 22个表单项（INPUT 类型按 Java 类型分组件）
11. `light-view/src/views/system/order/info.vue` — 22个 descriptions-item

### 注意事项
- SysOrder 是 `@MappedSuperclass`，实际不应直接映射数据库表，此处仅作 skill 测试
- `orderPrice` 字段有 `@Schema` 但无 `@AutoEntityField`，正确被排除
- `point`/`givePoint` 有 `@AutoEntityFieldDefault("0")`，add.vue 初始值使用 0

## Java 架构师视角的框架优化建议

### 背景
用户要求从专业 Java 架构师角度，对 Light 框架（含代码生成器）从架构设计、实用性、优雅性、可用性、开发效率5个维度给出优化建议。

### 深度分析发现的架构问题
1. **双 ORM 并存**：JPA（@Entity/@MappedSuperclass/Auditing）+ MyBatis-Plus（@TableId/@TableField/ServiceImpl）混用
2. **无泛型 CRUD 基类**：7+ 个 ServiceImpl/Controller 代码 90%+ 重复（listPage/export/save/find/delete 完全 copy-paste）
3. **注解包不统一**：`cn.light.common.anno`（生成器）vs `cn.light.common.annotation`（运行时）
4. **HtmlTypeEnum 前后端耦合**：后端 Entity 直接引用前端组件类型
5. **模板 bug**：日期格式 `yyyMMddHHmmss` 少一位 y；`Optional.of(id)` 用法无意义
6. **异常吞噬**：export 方法 `catch(Exception e) { throw new BaseKnownException(e.getMessage()) }` 丢失堆栈
7. **线程安全**：`Const.VUE_PATH` 是全局静态可变变量，并行流水线竞态
8. **错误依赖**：RateLimiterAspect 引用 `org.hibernate.service.spi.ServiceException`
9. **验证混用**：Jakarta Validation 注解 + Spring Assert 混合使用
10. **魔法数字**：错误码 500/1000/2000/10000 散布代码中

### 核心建议
- 引入 `BaseCrudService<M extends BaseMapper<E>, E, D, Q, L>` 泛型基类，消除 90% 重复
- 引入 `BaseCrudController<E, D, Q, L>` 泛型 Controller 基类
- 合并 anno/annotation 包，精简注解（正向声明替代 @InQueryDTO/@NotinListDTO 反向排除）
- 异常保留 cause 链：`new BaseKnownException(msg, e)`
- 定义 ErrorCode 常量枚举替代魔法数字
- 生成器支持增量 diff + dry-run 预览
- 修复线程安全问题，消除全局可变状态
